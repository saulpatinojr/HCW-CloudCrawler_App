## Known limitations of this slice

- Terraform state and plan evidence (ticket #54, ADR 0005) is read for 31 azurerm resource types (and the node pool, which
  joins its cluster) and says only what the document says: private endpoints (a separate resource), data sources, other providers, the `terraform show -json` form of a
  state and resources managed in another state are not read, and the plan route describes what Terraform would build. See
  "Terraform state and plan" in `docs/known-limitations.md`.
- Ten detectors (the wave-one set and the three Azure observation detectors) and fourteen tools (fifteen with a
  host); the ledger is in memory and not partitioned by tenant or session yet. The `cost-ceiling` detector and
  `cost_estimate_attach` are not in this slice.
- The Azure MCP host speaks stdio only. The HTTP transport to a hosted server under a managed identity or an
  on-behalf-of token (the Container Apps model of proposal section 10.2) is not implemented; `azureConnectivity`
  therefore reports `stdio-developer-credential` or `recorded`, never `managed-identity` or `obo`.
- The observation detectors ignore tag selectors (Advisor and policy rows carry no tags) and match the claim's
  `resourceTypes` against the recommendation's impacted type; a record whose rows all lie outside the decision's
  scope says nothing about it and the claim answers `unknown`. The caller class in `meta.caller` is declared here and enforced by the website's orchestrator, as
  the proposal says; this server checks only that a human-class call names an actor.
- The detectors read what a Resource Graph export carries, and the property names were taken from the Resource Graph
  schema on 2026-10-21 without a live query (no Azure access in the authoring session). A property an export omits
  (private endpoint connections on types where Resource Graph does not project them, `publicNetworkAccess` on older
  storage accounts) answers `unknown` with the property named, never a verdict.
- A single virtual machine row answers `unknown` for zone redundancy. The design's `instanceSet` claim parameter
  (VMs sharing a tag value form the set, supported when the set spans two or more zones) needs a set-level reader
  that this slice does not have; the reading says so.
- Resource Graph exports carry no diagnostic settings, locks or sub-resource encryption state; claims on those stay
  `unknown` until the App edition's collectors exist.
- `/api/health` reports `azureConnectivity: not-configured` unless `CC_AZMCP_MODE` names a host.
- Redaction (`_SECRET_SHAPED`) covers the secret shapes it knows and no others. Of a private key it replaces the header line only; `redact_payload` scans text values only. A match stops at the end of the second segment of a token, so the signature of a three-part token stays readable (unchanged), and a key value (`AccountKey=`, `SharedAccessKey=`, `sig=`) that runs straight into a token swallows the token's first segment (unchanged). When two secrets touch with no separator the match boundaries can differ from the pattern before ticket #53: a token whose second segment runs straight into a keyword (`<token>.<segment>AccountKey=<value>`, the same with `SharedAccessKey=`, `sig=` and the private key header) leaves the value readable, where the old pattern did the same unless a `ghp_` match pre-empted the token. `test_redaction_secret_shaped.py` counts such cases in a seeded fuzz (27 in 300,000) and sets ceilings; it is a sample, not a proof. The plain-words version is on the Known limitations page.
- Sign-in is **off by default**, and that is decided (owner, 2026-10-25, ADR 0004 "Owner decisions"). With `CC_AUTH_MODE=off`, `/api` and `/mcp` accept requests without any sign-in and the
  human-only tools only require a non-empty `actorId`; that is for a trusted lab network only (the README says so). Since the amendment of
  2026-10-26 the appliance **refuses to start** (exit 3) with sign-in off on a non-loopback address, unless
  `CC_ALLOW_UNAUTHENTICATED_NON_LOOPBACK=true` is set on purpose (then one `warning` line). The container image binds `0.0.0.0` and does not set
  the opt-out, so it needs sign-in on or the opt-out added by whoever runs it. The owner ran the README's real-tenant runbook on
  2026-10-26 (see "Ran for the real-tenant sign-in check"), and [ticket #8](https://github.com/saulpatinojr/HCW-CloudCrawler_App/issues/8)
  was closed as completed that day.
- Entra sign-in (ADR 0004) was **checked once against a real Entra tenant**, the owner's demo directory, on 2026-10-26: all seven
  calls of the runbook, the person check, the start-up refusal and the role gate answered as written, and a real version 2.0 token
  carried the `iss` (`https://login.microsoftonline.com/<tenant>/v2.0`), `aud` (the bare client id), `scp` (`access_as_user`) and
  `roles` (`CloudCrawler.Access`) values the checks assume. Still **not verified**: the version 1.0 `iss` form and the
  `api://<app id>` audience form (the setting takes both, but no version 1.0 token for this API was seen); the `idtyp` claim (the run
  did not report it); and the cases listed under "Did not run": TLS ingress or Container Apps behind a public host name, a service
  token from an application permission, an unassigned user when "Assignment required?" is on, an expired token, a token from
  another tenant, and signing-key rotation. Only the demo directory was used, so this says nothing about production. The `503`
  answer when the key set cannot be fetched is intended (owner decision, 2026-10-25), not a gap.
- Entra sign-in does not yet include: an allow-list of client applications (who can obtain a token is controlled in Entra by
  "Assignment required"); a per-tool permission model (since 2026-10-26 `CC_AUTH_REQUIRED_ROLES` adds one optional app-role gate for the whole
  service, empty by default, so by default any valid token for the tenant and audience can read, ingest, propose and evaluate); sovereign clouds (the public authority `login.microsoftonline.com` and
  `sts.windows.net` are fixed in `security/entra.py`); revocation (a stolen token works until it expires, as with any access
  token); token binding or proof-of-possession; rate limiting of failed sign-ins. A person's delegated token proves consent,
  not attention: an on-behalf-of service holding a person's token acts as that person.
- The tool schemas of `adr_accept`, `review_decide` and `collection_run_azure` now mark `actorId` optional (additive; the
  engine is unchanged). With sign-in off an empty `actorId` is still refused.
- The in-memory ledger is shared by everyone who can sign in; it is not partitioned by tenant, user or session yet, so a
  second tenant must not share one appliance.
- The labels of `.github/labels.json` and Discussions were not set up when the repository was created (`--skip-github`);
  whether that has been done since was not checked. The issue forms name labels (`needs-triage`, `architecture`,
  `decision`) that the repository did not have when last listed on 2026-10-25, and GitHub ignores a label that does not
  exist. `labels.json` still defines two labels (`finops-finding`, `terraform`) that no form or workflow uses.
